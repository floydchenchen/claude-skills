# Visual Concrete Explain（图 + 具体例子，第一遍就懂）

用户是 visual learner。抽象定义放在第一遍解释里，通常看不懂，每次都得追问「举个具体例子 + 画图」。这个 skill 的目标是**第一遍就给出那个版本**。

反馈历史：图本身做得不错，但单只把抽象定义用计算图/公式重说一遍还不够——每个抽象概念都得配一个「实际工作流里长什么样」的例子（真实规模的数字 + 真实工具/代码/命令行参数），不然解释会浮在公式和示意图之间，让人不知道这个概念在真实世界里对应的是什么。例：讲「数据并行：每张卡一份完整模型，分着吃数据」之后，必须接一个「训练中数据具体怎么切」的例子（真实样本数、真实 batch size、PyTorch DistributedSampler/DistributedDataParallel 这类真实函数名），而不是只给一句抽象总结就跳进去手算或画图。

## 核心原则

1. **例子先于定义。** 先拿一个最小的、能手算的具体例子走一遍，再告诉他「这就是公式说的事」。
2. **每个解释都要有图。** 不存在纯文字的解释。
3. **数字必须是真的。** 例子里的每个数都要跑脚本算出来并核对，绝不凭手感编。
4. **图里每个东西都要标注。** 没标注的点、线、颜色都会变成新的疑问。（教训：拔河图里两个没标注的灰点，导致他又追问了一轮。）
5. **ELI5 语言。** 中文，短句；术语第一次出现时用括号给一句白话解释。
6. **抽象句子必配实践例子，不能只靠手算图。**（新，教训）手算图证明公式对，但证不了「这个概念在实际工作中长什么样」。每讲完一个抽象概念的「一句话」后，紧接一个「实际场景」小框：真实规模的数字（不是 1/2/3 这种手算小数，而是像「10,000 条样本、batch size 256」这种真实会出现的规模）+ 真实工具/代码/命令行参数（函数名、CLI flag、配置项 key）。手算图回答「公式在算什么」，实践例子回答「我平时会在哪里用到它」。

## 最小例子怎么选

| 要求 | 做法 |
|---|---|
| 小到能手算 | 维度取 2，元素取 3 个（例：「我 爱 猫」，d = 2） |
| 数字简单 | 用 0/1/2 这类整数做输入和权重，结果保留两位小数 |
| 能画出来 | 2 维数据可以直接画成平面上的点，几何直觉最强 |
| 能复用 | 同一个例子贯穿全程：制卡 → 打分 → 混合 → 反例 → 下一步，不要每节换例子 |
| 有语义钩子 | 再配一个真实语义的例子（例：「吃苹果」vs「买一部苹果」），说明为什么这件事重要 |

这一节讲的是「手算玩具例子」（用来证明公式），下一节的「实践例子」是另一种，两种都要有，不能互相代替。

## 实践例子怎么配（新）

跟在每个抽象概念的「一句话」后面，回答「这在真实工作中是怎么发生的」：

| 要素 | 做法 | 反例 |
|---|---|---|
| 规模 | 用行业里真会出现的数字数量级（样本数、batch size、序列长度、GPU 数） | 别用手算玩具例子的 2/3/4 混在一起 |
| 工具 | 写出真实函数名/类名/CLI 参数/配置 key（PyTorch、HF Transformers、DeepSpeed、Megatron 都行） | 只说「用某个工具就能做到」不给名字 |
| 过程 | 说清楚数据/权重具体怎么被切、分到哪张卡、谁和谁通信 | 只说「分到各张卡上」而不说怎么分的 |
| 真实数字结果 | 把规模代入公式，算出真实会看到的结果（步数、提速倍数、显存 GB） | 只停在概念层面，不给最终数字 |
| 什么时候会遇到 | 描述真实会看到的现象（报错、OOM、loss 变 NaN、变慢） | 只讲原理，不讲会试发现什么 |

举例（数据并行）：「每张卡一份完整模型，分着吃数据」这句话后面接：

> 假设 10,000 条样本，想要 global batch size = 256，8 张 GPU。PyTorch 用 `DistributedSampler` 把数据切成 8 份不重叠的子集，每张卡拿到 256/8=32 条。每张卡用 `DistributedDataParallel(model)` 包一层模型，自己跟自己的 32 条跑 forward/backward，算出本地平均梯度，再 all-reduce 取平均。一个 epoch = 10,000/256 ≈ 40 步，而不是单卡跑的 10,000/32=313 步 → 快了 8 倍。启动命令大概是 `torchrun --nproc_per_node=8 train.py`。

这段同时满足了上面表格的 5 个要素：真实规模（10,000/256/8）、真实工具（DistributedSampler/DDP/torchrun）、过程（怎么切、谁和谁通信）、真实数字结果（40 步 vs 313 步）。

对于不确定的真实模型训练配置（比如「GPT-3 用了多少 TP/PP」这种具体数字），宁可用自己构造但现实的假设场景（写明是假设），也不要编造不确定的真实数字当事实陈述。工具名、函数名、CLI flag 这类可验证的事实要写准，不确定就略过版本号等细节。

## 解释的固定结构

```
① 一句话：这东西在干嘛（≤ 30 字）
② 实践例子：它在实际工作流里长什么样（真实规模数字 + 真实工具/代码/命令）
③ 生活比喻：派对 / 拔河 / 调颜料 / 开会，挑一个能对应到每个部件的
④ 全景图：数据怎么流动（流程图）
⑤ 手算玩具例子逐步走：每一步都写出真实算式和数字，每个元素挨个过一遍
⑥ 图：把第 ⑤ 步画出来（热力图 / 坐标图 / 柱状图 / 箭头弧线）
⑦ 「这说明了什么」表：现象 → 含义
⑧ 一句话记住（面试可直接说的版本）
```

② 实践例子是新增的必选步骤，紧跟在 ① 一句话后面、③ 生活比喻之前。两者分工：② 回答「我平时会在哪里遇到它」，⑤ 回答「它内部在算什么」。

按需增加：
- **常见误解**：用同一个例子算出反例（例：把「我爱猫」换成「猫爱我」，输出不变 → 证明 attention 不知道词序）。
- **下一步去哪**：这个结果之后会被怎么用，画出后续流水线。

## 图怎么画

| 场景 | 形式 |
|---|---|
| 聊天里的快速回答 | ASCII 流程图 + Markdown 表格 |
| 多步骤、值得反复看的主题 | 用 Artifact 发布 HTML 页面：内联 SVG + 可点击的逐步切换（例如点 我/爱/猫 切换当前 token） |

图型选择：

| 内容结构 | 图型 |
|---|---|
| 流程 / 数据流 | 横向方框 + 箭头流水线 |
| 谁关注谁 / 权重 | 弧线（粗细 = 权重）+ 柱状图，或热力图矩阵 |
| 向量 / 混合 / 加权平均 | 2D 坐标图：原料点 + 结果点 + 拉力线 |
| 前后对比 | 左右两栏 Before → After |
| 多个并行视角 | 小图矩阵（每个面板同一底图，只换高亮） |
| 实践例子（规模/工具/过程） | 独立的浅色调「实践」信息框，和手算图区分开，配等宽字体的代码/命令行片段 |

视觉规则：
- **颜色即语义，全程一致**：同一个概念在所有图里用同一个颜色（例：Q 青、K 橙、V 紫）。
- 每张图配 legend 或 caption，说清每种颜色 / 形状代表什么。
- 当前焦点高亮，其余元素变淡但仍然标注名字。
- 实践例子框在视觉上和手算/公式区分开（例如不同底色 + 等宽字体代码片段），让人一眼看出「这段是真实场景」。
- HTML 图做完后截图看一次，检查重叠、看不清的字和未标注的元素。

## 回答追问的模式

| 他问 | 怎么答 |
|---|---|
| 「这个在算什么？」 | 写出这个点 / 值的完整算式（逐坐标），再给一个比喻 |
| 「X 的意义是什么？」 | Before vs After 对比图 + 一个真实语义例子 |
| 「所以它是在算 Y 吗？」（理解有偏差） | 先直接说「不太对」，用同一个例子算出反例，再给一张「谁负责什么」表 |
| 「下一步是什么？」 | 画出后续流水线，每一步配比喻，并标出面试常考点 |
| 「这实际怎么用？/ 这在真实场景里是什么样？」 | 按「实践例子怎么配」的 5 要素给一段：规模 + 工具 + 过程 + 真实数字结果 + 什么时候会遇到 |

## 反模式

| ❌ 不要 | ✅ 要 |
|---|---|
| 先给公式和定义，最后才举例 | 先走例子，公式作为总结 |
| 只有手算玩具例子和公式，没有「实际怎么用」的实践例子 | 每个抽象概念的一句话后面配一段实践例子（新） |
| 例子太大（d = 512、10 个词） | d = 2、3 个元素，能在纸上手算 |
| 编造「看起来合理」的数字 | 用脚本算出来，文中数字和图完全一致 |
| 实践例子里的工具名/命令是编造或不确定的 | 只写确定正确的函数名/flag，不确定就略过版本号等细节，或明说是假设场景 |
| 大段中文段落 | 表格、图、短句 |
| 图里有没标注的点或线 | 每个元素都有名字，配 legend |
| 每节换一个新例子 | 一个例子贯穿到底 |
| 讲完就结束 | 结尾给「一句话记住」 |

## 收尾

- 用一句「一句话记住」收尾。
